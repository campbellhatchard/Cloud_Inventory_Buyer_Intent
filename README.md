# Summit Ct Guest Booking

Production-oriented v1 booking application for private guest accommodation. The two guest rooms are treated as one inventory unit: any approved or pending request blocks both rooms for the requested dates.

## Included in v1

- Public availability page that never exposes guest identity
- Booking request form with required name and optional email/phone
- Five-character booking reference using unambiguous uppercase letters and numbers
- One pending request allowed at a time
- Date-overlap prevention for pending and approved bookings
- Owner-only dashboard to approve, decline, or cancel requests
- Signed guest-management links for date changes and cancellations
- Password hashing and server-side owner session controls
- Audit-event records for material booking and login actions
- PostgreSQL production database on Render
- Render Blueprint deployment configuration
- Responsive mobile and desktop user interface
- Health-check endpoint at `/health`

Email delivery is intentionally deferred. The data model and signed management links are ready to be incorporated into approval, confirmation, decline, change, and cancellation emails in the next release.

## Render deployment

1. In Render, choose **New > Blueprint**.
2. Connect the `campbellhatchard/SummitCt` repository.
3. Render will read `render.yaml` and propose:
   - `summitct` Python web service
   - `summitct-db` PostgreSQL database
4. Set the required `ADMIN_PASSWORD` secret when prompted.
5. Deploy the Blueprint.

The configured owner username is:

```text
campbell.hatchard@gmail.com
```

Set `ADMIN_PASSWORD` in Render to the desired password. Do not commit that password to GitHub.

## Environment variables

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | PostgreSQL connection URL supplied by Render |
| `SECRET_KEY` | Generated by Render for sessions and signed links |
| `ADMIN_USERNAME` | Owner login username |
| `ADMIN_PASSWORD` | Initial owner password |
| `FLASK_ENV` | Use `production` on Render |
| `TOKEN_MAX_AGE` | Guest link lifetime in seconds; default is one year |

## Local development

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
export SECRET_KEY="local-development-key"
export ADMIN_PASSWORD="local-password"
flask --app app run --debug
```

Without `DATABASE_URL`, the application uses a local SQLite database for development only.

## Important operating rules

- An arrival and departure date are treated as occupied dates. A new request cannot start on an existing booking's departure date.
- Pending requests hold the requested dates.
- Only one pending request may exist globally.
- Changing an approved booking returns it to pending approval.
- Declining or cancelling a request invalidates its signed guest-management link.
- Public pages show booking dates but never guest contact or identity.
